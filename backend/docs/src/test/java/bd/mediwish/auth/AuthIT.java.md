# `AuthIT.java`

Source: [`src/test/java/bd/mediwish/auth/AuthIT.java`](../../../../../../../src/test/java/bd/mediwish/auth/AuthIT.java)

## Purpose

Exercises the password-session contract over real HTTP, PostgreSQL 18 and actual Liquibase migrations. Each test uses unique synthetic users and direct SQL only against the run-owned schema; `TestDatabase` removes that schema during teardown. The suite deliberately mutates persisted rows after issuing an access token so the current-user seam is tested against live state rather than token claims.

## Covered journeys

| Scenario | Contract evidence |
| --- | --- |
| Identifier login | Username, verified mobile and optional email identifiers all produce safe Bearer sessions and the same current profile projection. Email lookup ignores case; Basic authentication is explicitly rejected. |
| Generic failures | Wrong-password, unknown-identifier, unverified-mobile, cross-field identifier-collision, duplicate optional-email ambiguity and case-only email ambiguity failures use the same bounded authentication error shape without candidate disclosure. The exact-duplicate case creates three matching Users and confirms the repository returns at most two candidates. The case-only case changes one synthetic row to uppercase, tries both email casings, and verifies no cookie or session family is created. The current `upper(email)` expression index is confirmed non-unique and the obsolete exact-match index is confirmed absent. |
| Authentication privacy and runtime error redaction | Captured ECS output is checked through registration, successful/failed sign-in, CSRF bootstrap, refresh and logout for synthetic usernames, contacts, passwords, verifiers, access/refresh/CSRF credentials and caller request IDs. Error/logout response bodies and headers are checked for the same forbidden values; both deferred refresh and multi-session logout commit-failure cases require the generic 500 to omit the synthetic database exception from the response and structured output. |
| Unrelated order/payment/guest values | Synthetic order references, payment idempotency keys, a guest credential, a phone-shaped `X-Request-ID` and a valid-shaped random refresh cookie are tried at the login, refresh and profile HTTP seams. All are rejected generically, no refresh session cookie is issued, and the run-owned session row count is unchanged. |
| DeliveryPerson password session | A registered synthetic User is assigned `DELIVERY_PERSON` only inside the run-owned schema, then signs in through the public login API; the existing current-user seam resolves the persisted role and `/api/user/me` returns the safe profile. |
| Rotation and replay | CSRF-protected refresh rotates the opaque cookie. Reusing the consumed value returns a generic failure, revokes the family in PostgreSQL and invalidates the newly issued access and refresh credentials. |
| Rotation rollback at commit | A transaction-deferred constraint trigger in the run-owned schema is scoped to the test session's newly inserted generation 1. It raises only when PostgreSQL evaluates the trigger at transaction commit; the bounded 500 is followed by SQL assertions that generation 0 remains unconsumed and generation 1 does not exist. Captured ECS output must contain one final `status=500` event correlated to the response's server-generated request ID, not a premature 200. The trigger is removed in `finally`, after which the original cookie rotates successfully. |
| Post-commit response loss on the wire | A one-request loopback proxy forwards the refresh request, reads the complete upstream response headers, then closes both sockets without forwarding any response bytes. The upstream `200` and persisted consumed/new-generation rows prove the application committed before the client-side connection ended with an empty response. Retrying only the old cookie returns generic 401, revokes the family and makes the pre-rotation access token unusable. |
| Logout | CSRF-protected logout revokes the represented session family or families, clears the scoped HttpOnly cookie, invalidates the old access and refresh credentials, and remains safe to repeat. The stale-cookie retry assertion requires one revocation, the original session row and only generation 0 after the repeated logout. Duplicate cookies revoke every represented family; a deferred multi-family revocation failure proves the failed request leaves every family active and keeps the synthetic database exception and session credentials out of the response and captured ECS output. |
| Expired family and current identity | Expiring a persisted family invalidates both its existing access token and refresh cookie. Removing the persisted `CUSTOMER` role changes the old-token current-user seam while `mobile_verified=false` remains usable. Blank password verifiers and deleted User rows reject the old token with generic `401 AUTHENTICATION_REQUIRED`. The dedicated `Ticket03AuthorizationIT` supplies a test-only protected-authority rule on the existing profile path to verify role-based 403 without a production route. |
| Bearer identity database failure | A valid session reaches current-user loading after the run-owned `users` table is temporarily renamed. The real HTTP response remains a correlated, no-store `500 INTERNAL_ERROR`; captured output omits the PostgreSQL relation diagnostic and stack trace, and the table is restored in `finally`. |
| All-session revocation | `AuthenticationService.revokeAllForUser` is exercised with two independently issued session families; both access tokens and both refresh cookies become unusable, and PostgreSQL records both revocations. |
| CSRF and origin failures | Refresh and logout reject missing CSRF headers; invalid CSRF values and a disallowed Origin are rejected without consuming the refresh family. |
| Failure privacy | Login, CSRF, revoked-session, current-user and CORS failures assert bounded responses and absence of synthetic credentials, identifiers, access/refresh tokens and CSRF values from response bodies and headers. |
| Process-output and correlation privacy | Captured application output around synthetic registration/sign-in excludes identifiers and credentials. A separate captured-ECS test sends a numeric phone-shaped `X-Request-ID`, parses the actual correlation-filter log event, and asserts the caller value is absent from logs and HTTP output while the generated UUID matches the response header/error body/log field. It waits up to two seconds for the matching post-response 401 log event so the assertion is not racy with the server finishing the filter after the client receives the response. The deferred-commit failure case checks one final correlated 500 status event. |

## Test harness and privacy boundary

The suite uses Java `HttpClient`, the bounded CSRF bootstrap body, explicit `Cookie`/`X-XSRF-TOKEN`/`Origin` headers and response-cookie parsing. It starts with the explicit `test` profile, local Secure-cookie override and explicit allowed test origin. It asserts key sets, bounded body sizes, safe profile fields, status codes and cookie attributes; raw passwords, access tokens, refresh values, CSRF values and personal fixture values are not emitted as diagnostics. The duplicate-email journey checks that the query returns only two candidates even when three Users share an address, and that exact and case-insensitive lookup indexes remain non-unique; the index assertion checks PostgreSQL's rendered `upper((email)::text)` expression rather than only an `upper(` prefix. The case-only journey updates one synthetic row only within the `TestDatabase`-owned schema, then checks generic failures, no cookies and no session rows. Focused `OutputCaptureExtension` cases check registration/sign-in output, refresh and logout commit-failure redaction, actual ECS structured output, and suppression of database diagnostics when bearer identity loading fails. Direct SQL is limited to the isolated schema for synthetic email casing, role assignment/removal, family expiry, session absence, password unusability, User deletion, revocation counts, one temporary users-table rename restored in `finally`, and deferred failure triggers that are dropped in `finally`; the logout rollback test injects the failure in PostgreSQL, then verifies both represented sessions remain active through `/api/user/me`. The wire-loss case uses only a loopback one-request proxy, which inspects the HTTP status line but discards header values and all response bytes. No production endpoint or fault-injection seam is added.
