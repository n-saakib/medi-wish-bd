# ConcurrentRoleChangeIT

Sixteen forced cases exercise the role API through real HTTP and PostgreSQL in an owned test schema. Test-owned Mockito wrappers delegate to the real Spring beans and preserve their transactions; latches hold role revocation before or after its session locks, hold the first refresh-token save inside password sign-in and MFA verification, or hold authentication immediately after its active-session evidence read. No production hook decides the ordering. Competing operations must be observed in `pg_stat_activity` waiting on the expected User or session lock before release. The refresh-first case instead completes refresh while revocation is held before locking sessions. A repository delegate also gates one command before its User lock so an already-authenticated principal can be held across a completed demotion; the committed demotion response proves that ordering without a lock-wait poll.

Separate verified Admins race different roles in both orders, proving the first version wins and the loser receives `STALE_UPDATE`. Identical commands return the committed version without another audit or revocation. Distinct actors prevent a shared actor lock from hiding missing target locking.

The class provisions the real Super Admin before ordinary Admin fixtures. Both actor-demotion orders prove the command either commits before demotion, with its audit attributed to the actor, or the old token is rejected after the committed revocation without changing the third User.

An additional stale-principal case pauses an authenticated Admin command before it locks actor and target, commits the owner's demotion of that actor, then releases the command. Its independent role/session recheck must return bounded `403 ACCESS_DENIED` and leave the third User's Customer role, version, audit and active session unchanged. This preserves command recheck coverage now that requests starting after demotion fail earlier during authentication.

Both refresh orders require no usable target session afterwards: a refresh completed before revocation loses its new access token and cookie, while a refresh blocked behind revocation must be refused. Password sign-in is forced in both orders: after promotion it reads the committed role and opens a restricted session with the matching cookie lifetime; before promotion its new session is included in revocation. MFA verification likewise either finds its restricted session revoked or completes first and has the upgraded session revoked. Demotion retains the active authenticator.

Four promotion/authentication cases cover Admin search and UUID detail in both orders using a previously MFA-verified Moderator token. When authentication starts first, promotion must wait for its User share lock and the resolved Moderator receives bounded `403 ACCESS_DENIED`. When promotion starts first, authentication must wait for the User update lock, then receives bounded `401 AUTHENTICATION_REQUIRED`. Both read routes reject the old token afterwards and no active target session remains. The authentication-first fixture can reproduce the former leak: without the User lock it lets promotion commit while evidence is held and observes an erroneous Admin `200`; retained red evidence precedes the fix.

Assertions cover HTTP status and bounded errors, role/version/audit counts, session revocation, restricted assurance and lifetime, retained factors, and omission of tracked synthetic secrets from captured logs. Bounded latch and PostgreSQL waits always release during cleanup. The class carries integration, security, recovery and regression tags; the guarded AuthApi closes its application and owned schema.
