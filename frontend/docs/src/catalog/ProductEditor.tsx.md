# `src/catalog/ProductEditor.tsx`

Source: [`src/catalog/ProductEditor.tsx`](../../../src/catalog/ProductEditor.tsx)

The new and edit forms for a staff Product. New mode selects Medicine or Equipment and offers only active categories. It excludes Active, Pricing and Change history, sends no money or active field, and opens the saved Product. Edit mode keeps an existing inactive category visible and selectable, retains kind as read-only text, shows version/actor/status/history, and submits catalog and Admin pricing through distinct routes. History names catalog edits as “Details edited” and uses the typed new review flag to say “Review flag turned on” or “Review flag turned off,” matching the accepted audit copy. Change history renders each action and actor with a readable Dhaka-local date/time in a semantic `<time>` whose `dateTime` preserves the API instant. A Moderator sees disabled price values and cannot submit pricing.

Client validation names missing required fields, malformed or zero BDT amounts, price above MRP and activation without price. Pricing accepts the backend's exact positive decimal-string grammar: 1–7 whole digits and optional 1–2 fractional digits. It compares values as integer cents without floating point, preserves the entered strings in the request, and lets the server return normalized two-decimal values. Valid pricing submission clears prior money errors even when only the related MRP changed; pricing success clears a satisfied activation price error while preserving other catalog errors and the unsaved catalog draft. While either catalog or pricing saves, both forms disable their editable fields, category/kind choices, checkboxes and submit buttons, so the completed response cannot replace input typed during that request. The existing pending-ref guards also block repeated submissions including Enter. Controls become editable again after success or failure, respecting Moderator pricing permissions; failed requests retain the submitted draft. No-op edits skip the update. A stale version keeps the user's draft and offers Reload; a pricing response advances the version for the next catalog save. Initial load failure shows Retry before an incomplete form appears; a failed save keeps the draft and shows bounded error copy. A new draft retains one UUID across all create retries, including edits after an uncertain response. An identical retry recovers the stored Product; a changed retry returns the generic error without duplication or draft loss. On `ID_CONFLICT`, an explicit Reload opens the attempted UUID edit route so the operator can load the stored Product. `tests/catalogPages.test.ts` covers core mounted states and request guards; Ticket 14 browser tests cover the full role journey.

The current product status chip follows the list design: success green for Active, warning amber for Needs price and neutral for Inactive, always accompanied by readable status text.
