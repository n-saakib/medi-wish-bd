# Product image optimizer, races and recovery E2E checks

Mirrors `tests/browser/productImagesRecovery.spec.ts`.

The spec drives the real migrated API, isolated local object storage and built Next.js server. It reuses the catalog actors (independent authenticated sessions), synthetic image fixtures and strict image API helpers. All cases run on the configured Chrome and Edge projects; none is skipped or marked as an expected failure while Ticket 15 is unimplemented.

- **E2E-15-09:** anonymous WebP optimization and exact upstream protocol, host, port and public-path restrictions; external, metadata, protected, same-origin, query, unsupported-width and unsupported-quality requests return optimizer errors rather than API envelopes. A reachable controlled wrong-port listener serves a valid image; the optimizer must reject it before opening any connection, so upstream failure cannot masquerade as allowlist enforcement.
- **E2E-15-25:** PNG and JPEG removals plus both PNG→JPEG and JPEG→PNG replacements each issue two identical optimizer requests, requiring `MISS` and the exact 60-second cache header. The exact retired key must be absent immediately after the mutation response, before further requests; old optimizer/origin reads return 404 without polling. Replacement position, extension, format, dimensions and exact origin bytes are verified, and the browser independently decodes its optimized WebP dimensions.
- **E2E-15-27 replacement variant:** two verified actors queue the same id, bytes, alt and replacement target behind the real Product lock at eight images. Responses must be 201/200 with identical ImageViews even though the winner retires the target. The replacement retains a middle slot, the exact eight keys and independently captured sanitized bytes survive, all live public bytes match, the original disappears and returns 404, its id is retired, a later identical retry returns 200, and Product catalog state stays unchanged.
- **E2E-15-26–30:** last-slot uploads, duplicate upload replay at capacity, conflicting reorder and description commands, and overlapping remove/reorder preserve counts, winner state, versions, contiguous positions, public bytes and Product catalog state.
- **E2E-15-31–32:** removing PNG/JPEG and replacing across both formats retires the UUID globally: both PNG and JPEG reuse attempts on the original and another Product return `ID_CONFLICT`, preserve exact file sets, bytes, image lists and Product state, and both public/optimizer extensions remain unavailable; a same-id race across Products leaves exactly one live row/object and no object for the losing Product. This asserts the public invariant; it does not force the loser to reach the compensation branch before the winner commits.
- **E2E-15-33–35:** a controlled filesystem write failure returns a bounded 503 then retries the same intent; a missing object returns 404 while other files and metadata survive; a dedicated real HTTP client is disconnected after PostgreSQL proves its upload reached the Product lock; the server commits once and the exact intent replays with 200.
- **E2E-15-36:** concurrent PNG/JPEG replacements preserve one winning identity at the original position, retain the other image and its exact bytes, and retire/delete the original. Fresh control uploads establish each candidate's runtime-sanitized bytes; the winner's format, dimensions, byte size, file and public body must match that candidate. The exact object key set excludes both the retired original and a losing replacement object, and Product catalog state stays unchanged.
- **E2E-15-37:** an existing image row whose test object is missing cannot read the same key planted in a newly owned sibling `prod-` namespace. The public route and optimizer return 404, metadata and planted bytes stay intact, then the test object is restored and the probe namespace is removed.
- **E2E-15-38:** concurrent uploads of the same id with differing bytes or alt text at the last slot admit one intent and return `ID_CONFLICT` for the other. Fresh control Products independently upload both candidates to capture this server runtime's re-encoded bytes, requiring distinct results for the bytes variant. Exact winner file/public bytes and all seven existing object bytes are checked before replay, after successful replay and after loser refusal; exact object names/count and Product/image state stay unchanged.
- **E2E-15-39:** a dedicated real HTTP client is disconnected after its replacement reached the Product lock, and the server commits the new image once. Replaying its exact intent succeeds despite the now-retired replacement target; the original is unavailable, the new identity retains its slot, and the other image survives.
- **E2E-15-40:** a controlled Product-directory blocker makes a replacement return a bounded 503 without retiring its original or altering metadata. The owned directory is restored in `finally`; original bytes still match. Retrying the same intent replaces once and replays with 200.
- **E2E-15-41:** differing orphan bytes planted at a fresh replacement key cause `ID_CONFLICT`. The orphan, original live image and unrelated image remain untouched, and the fresh id is not public. Removing only the planted orphan permits the exact replacement intent to succeed.
- **E2E-15-42:** PNG/JPEG append and replacement recover a same-byte orphan at a fresh intended key without an image row. A real control upload establishes runtime-sanitized bytes, which match its public body and local file. Before adoption the orphan is private and lists/files are exact; adoption returns 201, leaves exactly one live row/object with those bytes, preserves Product state, and its exact subsequent replay returns 200 without change. Replacement retains the slot and retires/deletes its original. This directly constructs the storage/row gap and does not claim a process restart. Failure cleanup removes only the exclusively planted unreferenced key; live adopted bytes remain owned by namespace teardown.
- **E2E-15-43:** replay after reorder returns the current position; after a description edit the old description yields `ID_CONFLICT` and the current description returns 200 with the updated version. Exact image lists, object names/bytes, both public bodies and Product catalog state remain unchanged by every replay/refusal.
- **After-commit remove/replace faults:** a nonempty owned directory at the original object key makes physical deletion fail after commit. Both commands retain their 204/201 success and emit one warning scoped by their response request id in the structured ECS log. The test waits only for the matching HTTP completion log record, since the filter's finally block can run after response receipt; it parses complete newline-terminated JSON and then asserts exactly one warning once. The warning names an exception class, carries no throwable/stack field, and excludes object paths/keys/ids, raw filesystem messages, private alt text and bearer secrets. Ordinary HTTP log metadata is not subjected to the warning-only identity restriction. The old id is retired and public/optimized reads return 404; the unrelated image and any replacement remain live. Cleanup restores the original bytes as an unreferenced orphan at its key, which remains private and is removed by run namespace teardown. No orphan sweep is assumed.

The shared `productImageConcurrencySupport.ts` fixture uses one owned `psql` child to lock only newly created synthetic Product rows. `blockedRequests` observes `pg_blocking_pids` until every request is queued, proving overlap without scheduling sleeps. `race` awaits requests after releasing the lock, including assertion failure paths. The lock client rolls back and exits in `finally`; a watchdog terminates only that child if it fails to exit. The helpers require the checked run schema and an explicit loopback test database on isolated port 55432 or 55433. Dedicated units verify their guards and cleanup.

Filesystem failure fixtures use the guarded `imagePath` under `MEDI_WISH_TEST_STORAGE_DIR`. They create a blocker only at a new Product's directory and remove it in `finally`, or temporarily rename an owned image or Product directory and restore it in `finally`. The replacement-outage case removes its blocker before restoring the owned Product directory, including assertion-failure paths. After-commit deletion faults similarly remove only their owned blocker file/directory, then restore the original bytes as a private orphan. Create-only collision cleanup unlinks only the fresh key planted with exclusive creation. E2E-15-37 alone creates a sibling probe namespace derived from the checked storage root: non-recursive creation refuses any existing directory, and `finally` removes only the directory that this invocation created. Global setup owns ordinary fixture teardown.

HTTP headers establish the accepted cache bound; an already rendered document can continue displaying its existing image until it renders again.

E2E-15-09 exercises both PNG and JPEG as real uploaded optimizer sources, requiring WebP content type, RIFF/WEBP framing and a complete declared RIFF length. The browser independently decodes returned WebP bytes with `createImageBitmap` and checks preserved dimensions for these small fixtures, which the pinned optimizer resizes with `withoutEnlargement`. The browser also independently decodes the uploaded fixture bytes and compares opaque alpha and mean absolute RGB error against the optimized pixels. Fixture-specific bounds are 55 for the deliberately noisy PNG and 3 for the flat JPEG: the installed Sharp quality-75 outputs measure 46.6415 and 1.1667 in both Chrome and Edge. These bounds tolerate the pinned lossy codec while rejecting same-size unrelated content; they are not universal image-fidelity limits. Exact-source assertion probes accept legitimate quality-75 output and reject blue/gray placeholders, a different PNG seed and a spatially flipped PNG. The source format must not determine whether the accepted public allowlist can optimize it.

Optimizer refusal checks allow an absent content-type header while still rejecting JSON and image content types, requiring HTTP 400, no request correlation and no leaked bounded-API envelope. Missing headers are ordinary Next refusal behavior, not a successful image response.

The lost-response cases dispose only their dedicated request context after observing the blocked server transaction, then release the Product lock immediately. They preserve the application's existing three-second JDBC socket timeout; waiting eight seconds for an HTTP timeout would instead trigger a database failure before the client disconnected. Both disposal and lock release run in `finally`, while metadata, replay status, public availability, identity and storage assertions remain intact.

The disallowed-upstream-port fixture derives the configured API origin and substitutes isolated port18116, so the assertion remains distinct when Ticket15 uses18115.
