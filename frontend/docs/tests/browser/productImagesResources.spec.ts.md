# Product image resource end-to-end measurements

`tests/browser/productImagesResources.spec.ts` implements Ticket 15 T7's real-stack resource evidence on the built frontend and real API, PostgreSQL and isolated local storage. It uses eight independent 1024 × 1020 RGB PNG fixtures, each above 99% of the accepted 3 MiB input limit, and records upload wall time, input size and sanitized stored size.

The test measures the eight-image list response against the existing 16 KiB client bound. It requests one image twice at each of widths 640 and 3840, verifying WebP, `X-Nextjs-Cache: MISS` and the accepted 60-second cache header on every response. The browser independently decodes every sequential and burst response, requiring 640 × 638 at width 640 and the original 1024 × 1020 at width 3840 (the pinned Sharp optimizer forbids enlargement). Width 640's output must be smaller than the stored noisy RGB image. It then sends sixteen independent optimizer requests concurrently (eight image identities × two widths), recording each status, output size, cache result and elapsed time, plus the total burst time and 5xx count. Every burst request must succeed as decodable WebP with the expected dimensions, a MISS and the same exact 60-second cache header; no latency SLA is invented.

The synthetic measurements are retained in the `ticket-15-resources.json` Playwright attachment and `t15-resources` annotation. The test has `@t15`, `@t15-T7` and `@resources` tags and a bounded three-minute execution timeout. Its local decoding and dimension helpers introduce no dependency or new process lifecycle.

Peak frontend working-set measurement remains an explicit manual T7 gate: sample the built frontend's `WorkingSet64` during the burst on native Windows and retain its peak, process identity, command and build revision with the run evidence. The JSON records `peakWorkingSetBytes: null` and an `outstanding-check` annotation until that evidence exists. Sequential elapsed time and the burst's successful responses do not prove memory pressure. The fixture also does not replace the backend's separate worst-case 16-bit 4096 × 4096 decode allocation or query-count measurements, and no Ticket 59 release load acceptance is claimed.

All sixteen optimizer attempts settle before assertions or fixture cleanup. HTTP responses retain status, bytes and elapsed time; transport/body-read failures retain the synthetic image index, width and elapsed time with a boolean network-failure marker and no exception text or URL. The JSON attachment and annotation are written before burst assertions, so failed bursts retain evidence, including network-failure, decode-failure and 5xx counts. Browser decoding starts only after all HTTP attempts settle and lies outside the recorded request elapsed times; decode errors retain response measurements without raw exception text or bytes in the attachment.
Burst start and completion Unix UTC milliseconds permit exact correlation with separate native Windows process-working-set samples. The ignored T7 sampler identifies the listening Next process on port 3115 and records PID, UTC milliseconds and WorkingSet64 repeatedly; combine only samples inside the actual burst window.
