# `tests/browser/staffRolesApi.spec.ts`

Source: [`../../../tests/browser/staffRolesApi.spec.ts`](../../../tests/browser/staffRolesApi.spec.ts)

## Purpose

Ticket 08's end-to-end API tests: the role routes (`POST /api/admin/users/search` with the filter in the JSON body, `GET /api/admin/users/{id}`, `PUT /api/admin/users/{id}/roles` with `{ role, rolesVersion }`) called directly against the test API through [`apiSession.ts`](apiSession.ts.md), on the `chrome` and `msedge` projects. Every User holds exactly one role, and higher roles inherit lower ones (DECISIONS S6). Each test registers its own synthetic Users and reads the role, audit and session tables through [`apiSession.ts`](apiSession.ts.md) and [`sessionStates`](testApi.ts.md). Test IDs, tags and the acceptance criteria each covers are listed in §10 of the Ticket 08 implementation plan.

## Tests by sub-ticket tag

- **`@t08-T2`** (`E2E-08-51`): the database. A second `user_roles` row for a User is refused by `pk_user_roles`; a transaction that would commit a User with no role (a User inserted without one, their only role deleted, or their only role deleted and then their `users.id` changed) fails the deferred `user_role_required` constraint triggers, while deleting and re-inserting the role in one transaction commits; only the four roles can be stored (`ck_user_roles_role`), and the audit accepts every real old → new transition, including to and from `CUSTOMER`, and refuses unknown or unchanged roles; all probed inside rolled-back transactions.
- **`@t08-T4`** (`E2E-08-01`–`09`, `E2E-08-50`): routes, authorization and validation. Anonymous and forged tokens get `401`; Customers, DeliveryPersons and verified Moderators `403 ACCESS_DENIED`; restricted Admin sessions (enrollment or code pending) `403 MFA_REQUIRED`, also from the Moderator- and Customer-level routes, because they hold no role authority for the hierarchy to extend. The role hierarchy: every role reaches `GET /api/user/me`, the Admin (holding only ADMIN) reaches the Moderator-level `GET /api/staff/me`, and no lower role reaches a higher route. The search's summary shape, defaults (an empty filter), byte-order sort by username and `no-store`; malformed search filters (including unknown properties and non-object bodies), ids, unknown roles, the old `staffRoles` array and other bodies → `400`; an unknown id → `404`; the `PUT` CORS preflight from the frontend origin only, and no CSRF token needed.
- **`@t08-T5`** (`E2E-08-10`–`19`, `E2E-08-52`): the joined backend. Setting MODERATOR replaces CUSTOMER, returns the documented body and revokes both of the target's independent sessions, each access token and refresh cookie (`role-changed`); the I1 lifecycle (promotion → enrollment, demotion to CUSTOMER → `NOT_REQUIRED`, re-promotion → `VERIFICATION_REQUIRED` with the kept authenticator); DELIVERY_PERSON adds no MFA; every change among Customer, DeliveryPerson and Moderator replaces the one stored role, is audited and revokes; one audit row per change with the response's `X-Request-ID`; stale versions → `409 STALE_UPDATE`; own-role changes → `409 ROLE_CHANGE_REFUSED` while the current role is a `200` no-op; S5 (an ordinary Admin never sets ADMIN or replaces an Admin's role, checked before the version); the Super Admin promotes to Admin and demotes to Moderator and Customer; the Super Admin's role is never replaced, by anyone; search filters (prefix, case, literal `_` and `%`, exact role, paging, `staffMfa`) and no private fields.
- **`@t08-T6`** (`E2E-08-20`–`27`): R1 regression (a Moderator cannot self-promote), mass assignment, a 17 KiB role change, a valid search filter padded past 16 KiB (the same filter unpadded lists the User) and `text/plain` → `400`; concurrent different saves (one `409`), concurrent identical saves (one row), a demotion racing the demoted Admin's own save, a change racing the target's refresh, a lost-response retry, and immediate loss of a Moderator demoted to Customer.
- **`@t08-T7`** (`E2E-08-28`): bounded payloads (at most 50 Users a page; the latest 20 of 21 role changes).

Not covered here (plan §10.6): Moderators reaching DeliveryPerson-level routes (none exist yet; Tickets 40 and 41), the migration's conversion of existing multi-role Users and first-Admin provisioning replacing CUSTOMER (backend ITs). The `Promise.all` races of `E2E-08-22`–`25` check outcomes only; the deterministic orderings (a lock held by a second connection) and the rollback and restart cases are backend ITs in plan T6.

## Running

Build the backend jar first, then run one gate at a time, for example `npm run test:browser -- --grep @t08-T5`. Gates are cumulative: sub-ticket N's gate is every `@t08-T1`…`@t08-TN` test (plan §10).
E2E-08-25 distinguishes both refresh outcomes: a successful racing refresh leaves its cookie to be refused with 401; a racing 401 must have the bounded envelope and cleared cookie, after which a cookie-less refresh correctly returns 204. The token must still be fresh and rejected with 401 in both outcomes. This preserves the revocation assertion without mistaking signed-out behavior for a second cookie rejection.
